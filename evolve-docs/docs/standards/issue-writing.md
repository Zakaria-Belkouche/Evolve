# Issue Writing Standard

## Philosophy

**An Evolve issue should clearly explain what needs to be achieved and why, while avoiding unnecessary prescription of how it must be implemented.**

Evolve is both a project and a learning environment. Issues should leave room for investigation, problem-solving, and engineering decision-making rather than defining the solution from the outset.

## Common Approaches

* **Lightweight** — Only the essential information.
* **User-Story Driven** — Describes work from the user's perspective.
* **Outcome-Driven** — Defines the problem and desired result.
* **Specification-Driven** — Defines detailed requirements and acceptance criteria.
* **Task-Driven** — Defines a specific piece of work.
* **RFC / Design-Driven** — Investigates and designs before implementation.

## Evolve's Approach

Evolve uses a **lightweight, outcome-driven approach**. Issues should define **why** the work is needed, **what** should be achieved, and **when** it is considered complete.

Detail should be proportional to the complexity of the work.

## Default Structure

```md
# <Title>

## Context

Why is this needed?

## Goal

What should be achieved?

## Done When

- Outcome 1
- Outcome 2
```

## Example

```md
# Establish a Documentation Strategy

## Context

Evolve needs a consistent approach for storing and maintaining its growing technical documentation.

## Goal

Decide how Evolve's documentation should be stored and organised.

## Done When

- A documentation approach has been selected.
- The reasoning has been documented.
- An initial structure has been created.
```
